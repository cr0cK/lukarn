# 1.2.0 — Storage becomes an interface, with three more backends

**Target.** The interface, plus a local folder, an S3-compatible bucket and a
WebDAV server, with several connections live at once: one instance serves an
album from a Drive and another from a MinIO. Connections are managed from
`/admin`, which is also what makes a second backend usable without editing `.env`
and restarting the container.

Delivered as **four successive pull requests**, each building on the previous
one's interface.

### What PR 1 landed

`storage/provider.ts` declares `StorageProvider` — the **three operations that
actually reach a storage**: `list`, `fetch`, `preview` — plus `probe()` for
/admin and `guard()` for failure translation. `storage/drive.ts` implements it and
is the only file importing `@googleapis/*`; `drive/` became `storage/` and
`sync/`. The error taxonomy is `Storage*Error` and the three media error codes are
`storage_*`. See
[D260815f](../08-decisions/D260815f-a-storage-interface-and-drive-as-its-first.md).

### What PR 2 landed

`storage_connections` (migration 17), `albums.connection_id`, `media.source_path`;
`StorageConnectionRepo` and `StorageRegistry`; seven `/api/admin/storage` routes
and the Storage section of /admin. Review added a per-album connection check to
the prewarming and transcoding passes: gating on "is any storage connected" while
iterating every album let one revoked connection burn a second per photo, per
pass — the exact waste D61 added the instance-wide gate to prevent. See
[D260815g](../08-decisions/D260815g-the-single-row-oauth-token-table-becomes-a-table-of.md).

## The two facts that shape the rest

1. **The server never parses EXIF.** Drive delivers it pre-parsed in
   `imageMediaMetadata`, which is what `StorageEntry.media` carries. No other
   backend does: `media` is `null`, and capture date, camera, ISO and GPS have to
   be read from the bytes — through a ranged 64 KB window, exactly like the MP4
   header reads in `sync/sync.ts`, so that indexing without downloading (D3)
   survives.
2. **There is no local preview path.** `MediaRenderer` falls back to
   `provider.preview()` whenever sharp cannot decode a file, which is the only
   source of video posters (D92) and of HEIC/RAW previews. Other backends hold
   none and answer `null`; ffmpeg is already in the image and takes over for
   video.

## What changed since this plan was first written

Read this before following the checklists: six points below are already done, or
done differently.

- **`repo.getFileMeta` already returns `connectionId` and `sourcePath`.** The read
  side of media identity is finished; PR 3 owes only the write side.
- **`SUPPORTED_KINDS` in `storage/registry.ts` gates what `POST /api/admin/storage`
  accepts**, and it is `['drive']`. A kind is not creatable until it is listed
  there, and `AdminStatus.storageKinds` reports the list to the add form. This did
  not exist when the plan was written.
- **The /admin add form collects `id`, `kind` and `label` only.** The API accepts
  `settings` and `secret` on create and patch; the form has no fields for them.
  The `authorization: 'settings'` branch is declared and unimplemented — the local
  subpath field belongs to PR 3, the endpoint and key fields to PR 4.
- **`MediaRenderer.render` / `.prepare` and `Transcoder.transcode` take the
  provider as their first argument.** They no longer hold one: one renderer serves
  every album, and albums no longer all read the same storage.
- **`config/albums.yaml` has no `connectionId` field** (`config.ts`). A fixture or
  a bootstrap file cannot declare which storage an album reads; it goes through
  `ConfigRepo` or the admin route.
- **Decision identifiers are the date they are written**, so the ones below take
  the writing session's date, not this plan's.

## PR 3 — A local folder, and EXIF read from the bytes

The first non-Drive backend, and the proof the interface holds.

- [ ] `STORAGE_LOCAL_ROOT` in `env.ts` (default empty = the kind is unavailable),
      in `.env.example`, and in the `environment:` block of `docker-compose.yml` —
      D78 is checked by `check:specs`, and a variable that does not reach the
      container is not configurable. A commented `./photos:/photos:ro` volume goes
      with it. **`/admin` chooses a subpath under that root, never an absolute
      path**: the fence is declared by whoever runs the container, not by whoever
      administers it.
- [ ] `storage/local.ts`: `readdir(…, { withFileTypes: true })` for `list()`,
      `version = ${size}:${mtimeMs}`, MIME from the extension. `fetch()` returns a
      `Response` built from `createReadStream(path, { start, end })` via
      `Readable.toWeb`, so `routes/media.ts` is untouched. `preview()` returns
      `null`. Every resolved path goes through `realpath` and is checked to still
      sit under the root — a symlink out of the tree is the vulnerability here.
- [ ] Make the kind reachable: `'local'` in `SUPPORTED_KINDS`, its `case` in
      `createProvider`, and the subpath field in the add form under the
      `authorization: 'settings'` branch.
- [ ] `sync/exif.ts`: pure, in the style of `mp4.ts`. `findExifSegment(buffer)` for
      the JPEG APP1 marker, the HEIC `meta`/`iloc` path reusing the box walker
      already in `mp4.ts`, then `exif-reader` for the TIFF IFDs. New dependency:
      `exif-reader` (~30 KB, MIT, sharp's companion) rather than re-implementing
      IFD parsing — same reasoning as D5.
- [ ] `sync/sync.ts`: when `entry.media === null` and the file is a photo, read one
      64 KB window and parse it — the same shape as `videoHeader`/`readWindow`,
      with the same shortcut (`MediaRepo.fileTakenAt`: skip when `version` is
      unchanged and `takenAtFromExif` is already true). One extra request per new
      photo, none on subsequent passes.
- [ ] `sync/metadata.ts` gains an adapter from `exif-reader`'s output (real
      `Date`s, GPS rationals with N/S/E/W refs) to `ProviderMediaMetadata`.
      `parseExifTime` keeps handling Drive's `YYYY:MM:DD HH:MM:SS` string.
- [ ] Media identity: `mediaId(connectionId, path)` = `sha1(connectionId + '|' +
path)` truncated, with the path stored in `media.source_path` —
      `MediaUpsert` gains `sourcePath`, and `toUpsert` fills both. Note the
      accepted cost: **renaming a file gives it a new id, orphaning its
      comments** — Drive is the only backend whose identifier survives a rename.
- [ ] Video posters without a backend preview: an ffmpeg still (`-ss`,
      `-frames:v 1`), reusing the `run()` seam in `media/transcode.ts`. This
      supersedes **D92** and needs its own decision file saying why the trade-off
      changed. HEIC and RAW without a backend preview have no preview — a
      documented limit, not a bug.
- [ ] **Decide what `hasPreview` means for a local video.** `StorageEntry.hasPreview`
      becomes `media.has_thumbnail`, and `routes/media.ts` returns **415 before
      rendering** when it is 0. A local backend answers `false`, so every local
      video would refuse its thumbnail before ffmpeg is ever asked. Either the
      indexer sets it from "ffmpeg is available and this is a video", or the route
      stops treating the column as the whole answer. This is not in the original
      plan and blocks the poster work.
- [ ] E2E: `packages/e2e/specs/storage.spec.ts` — declare a local connection over a
      fixture folder of a few real JPEGs, resync, watch the album fill. This is the
      **first end-to-end test of a real sync**; the suite has never had one because
      Drive was deliberately absent. `fixtures/instance.ts` must name
      `STORAGE_LOCAL_ROOT` (its comment says every variable `env.ts` reads is listed
      there, so a developer's `.env` cannot leak in), and the connection is created
      through `StorageConnectionRepo` in `fixtures/prepare.ts` — the bootstrap YAML
      cannot name one.
- [ ] Docs: `specs/02-architecture.md` (the sync flow gains the metadata branch),
      `specs/06-configuration-and-deployment.md` (the variable, the volume),
      `specs/04-security-and-access.md` (path traversal),
      `specs/01-vision-and-scope.md` (the scope row). Decisions: _EXIF is read from
      a 64 KB window_, _a media identifier is a hash of its path when the backend
      has none_, _a video preview is produced by ffmpeg when the backend has none_,
      _a local root is declared by the environment, not chosen in /admin_.
      `CHANGELOG.md` under `## [Unreleased]`.

## PR 4 — S3-compatible, and WebDAV

Both reuse everything PR 3 built; only the listing and the signing differ. They
can be split into two parallel branches once `storage/xml.ts` exists.

- [ ] `storage/xml.ts`: a minimal element reader (~60 lines, no dependency) shared
      by both — enough for `<Contents>`, `<CommonPrefixes>` and `<d:response>`.
- [ ] `storage/sigv4.ts`: AWS SigV4 signing over `fetch`, **rather than
      `@aws-sdk/client-s3`** — the SDK weighs some 15 MB with dozens of transitive
      dependencies for three request shapes, and its streaming body does not map
      onto the `Response` the media proxy relays. Same reasoning as D5. Tested
      against the published SigV4 test vectors.
- [ ] `storage/s3.ts`: `GET /?list-type=2&prefix=…&delimiter=/&continuation-token=…`
      for `list()`, `version` = ETag, ranged `GET` for `fetch()`, `preview()` null.
      Settings: `endpoint`, `region`, `bucket`, `prefix`, `pathStyle` (MinIO needs
      it); secret: `accessKeyId` + `secretAccessKey`, stored as JSON in the one
      encrypted string a connection has.
- [ ] `storage/webdav.ts`: `PROPFIND` `Depth: 1` asking for `getcontenttype`,
      `getcontentlength`, `getlastmodified`, `getetag`, `resourcetype`; `version` =
      `getetag`; Basic auth with an app password; ranged `GET` for `fetch()`.
- [ ] `SUPPORTED_KINDS` gains both, `/admin` gains their forms and i18n keys, and
      the `test` probe is wired to real error text (a wrong key, an unreachable
      host, a missing bucket).
- [ ] Tests: `storage/s3.test.ts` and `storage/webdav.test.ts` against a local HTTP
      stub — no network in `pnpm test`.
- [ ] Docs: `specs/02-architecture.md`, `specs/05-api.md`, `README.md` ("connects a
      Drive" → "connects a storage"). Decision: _S3 requests are signed by hand
      rather than with the AWS SDK_.

## Verification

Per pull request, in this order, and the work is not reportable before both are
quoted:

```bash
pnpm verify        # typecheck, lint, format, tests, check:specs, check:links, check:changelog
pnpm test:e2e      # Playwright, the built server, WebKit + Chromium (~2 min)
```

`pnpm test:e2e` needs `pnpm build` first — it starts the **built** server — and
`pnpm exec playwright install chromium webkit` once. It is deliberately not part
of `verify` (D260814g).

`check:specs` is the one that will bite: every new module basename must appear in
`specs/**` **outside this directory**, every new environment variable must appear
in `specs/06-configuration-and-deployment.md` **and** be wired in
`docker-compose.yml`, the migration count in `specs/03-data-model.md` must match
`db.ts`, and the last segment of every new route must appear in `specs/05-api.md`.

Beyond the gates, per pull request:

- **PR 3** — a folder of a hundred real photos, mixed JPEG/HEIC/MP4: dates,
  camera, GPS and posters compared against the same folder synced from a Drive.
- **PR 4** — against MinIO in Docker and a real Nextcloud, both with a `Range`
  request on a large video (this is where an unsigned or mis-signed byte range
  shows up).

Neither has been done: no environment in which these branches were written had a
Drive account, a bucket or a Nextcloud. PR 1 and PR 2 carry the same gap, stated
in their pull request bodies.
